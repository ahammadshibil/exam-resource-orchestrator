# Project rule

Build a small tool that solves one problem reliably. Expand only after proving it helps.

The current focus is a learner with a torque misconception: identify the difficulty, offer a relevant original section with a concrete study task, then assess a fresh unaided response.

Prioritize changes that improve this flow. Catalog size, feature count and README polish are not success measures. Keep other existing capabilities working, but defer expanding them until this flow has evidence of usefulness.

Keep these distinctions explicit:

- A passing automated check demonstrates software behavior, not learning effectiveness.
- Synthetic responses and supplied rubric marks must be labeled as synthetic.
- A link click or reported study completion does not establish mastery.
- LearnHarness sessions/graph and Python assessment history are separate unless an actual integration is implemented and verified.
- Live learner validation remains pending until a real session has been observed; never describe the fixture demo as that evidence.

Run checks appropriate to each change, preserve source attribution, and make focused edits. Follow the additional instructions inside `learnharness/` when editing that app.
